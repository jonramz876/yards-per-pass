## Data pipeline

- `scripts/ingest.py` downloads nflverse parquet files (PBP, rosters, participation) and upserts into Supabase. Run: `python scripts/ingest.py --season YEAR` (or `--all`, `--dry-run`).
- `DataNotYetPublished` exception: a 404, empty file, or zero usable REG plays on the **current** season is a benign skip (exit 0, clear log). Any non-empty current-season file with real plays is ingested — even a single game (~180 rows), per Jon's "update every night after at least 1 game" requirement. Historical seasons keep the 1,000-row minimum and fail loudly.
- Truncation guard: ingest refuses to write if the new file's max week is lower than `data_freshness.through_week` (protects against nflverse re-publishing a truncated file; `cleanup_stale_rows` would otherwise delete players/teams). Accepted residual risk: a sparse republish that keeps the latest week would pass the guard.
- nflverse publishes `play_by_play_{year}.parquet` only after the first games are played; rosters appear earlier.
- **Flags added 2026-10-06:** `--state-file PATH` (skip when sources are unchanged; only the scheduled workflow passes it) and `--force`. Without `--state-file` every run is a full run with DDL, as before. `process_season` returns `{participation_loaded, source_digests, rows_sent, through_week}` and takes `ensure_schema=`; `ingest_schedules` takes `ensure_schema=` and returns the row count. **A new `ensure_*` function must** start with `SET LOCAL lock_timeout = '10s'`, commit once, be called inside `process_season`'s `if ensure_schema:` block, and be added to `ALL_ENSURE` in `tests/test_refresh_ddl.py` (a test fails until it is). Any edit to `ingest.py` triggers one full run and one DDL pass by itself.
- **`validate_data` low-volume rule (PR #27, 2026-09-29):** the `epa_per_db` ±5 check applies only to QBs with ≥ `EPA_DB_CHECK_MIN_DROPBACKS` (10) dropbacks; lower-volume outliers log a warning. It used to abort the whole season write — A.Dalton's single 2026 dropback (a pick at CHI −9, −5.57 EPA) blocked every refresh after Week 3 MNF. Columns are coerced with `pd.to_numeric`; unknown/negative/boolean dropbacks count as high volume (still checked). Any new per-player range check must think about 1-play samples the same way. Tests: `tests/test_validate_data.py`.
- **nflverse publish timing (week 1 2026):** PBP updates are usually hand-triggered by a maintainer soon after games — ~03:20–06:10 UTC after night games, ~21 UTC for Sunday's early window (all 15 week-1 Sunday games were up by 04:23 UTC Monday). Their unattended scheduled builds land ~10–14 UTC. Uploads use `gh release upload --clobber`, so the file 404s for a few seconds per upload.

## GitHub Actions (jonramz876/yards-per-pass)

- `data-refresh.yml` ("Nightly Data Refresh" — name kept for run-history continuity) — since 2026-09-14 runs **every 4 hours at :17 UTC September–February** (01:17 / 05:17 / 09:17 / 13:17 / 17:17 / 21:17 UTC) and **only 13:17 UTC March–August** (offseason skip + keepalive, same as before). Auto-targets the current season.
- **`concurrency: data-refresh`, `cancel-in-progress: false`**: a refresh that arrives while another is running waits for it; if several pile up, the newest waiting run replaces the older waiting one. A grey **"cancelled"** run in the Actions tab is therefore normal, not a failure. Runs are never cancelled mid-transaction.
- **GitHub starts scheduled runs 2–6h late** (3.3–5.6h in Sept 2026) at every time of day — an off-peak minute does not help (nflverse tried). The *gap between runs*, not the start time, controls how fresh the site is. Manual `workflow_dispatch` runs start within seconds. If six runs a day proves too slow (GitHub dropping runs, 8h+ delays), the fallback is an outside timer calling the `workflow_dispatch` API.
- **Before running `seed.yml` or a local `py -3 scripts/ingest.py` against production**, check `gh run list --workflow data-refresh.yml --limit 3` for an in-progress refresh. Seed and local ingests are not in the concurrency group, pass no `--state-file`, and so still run all 18 `ensure_*` DDL functions every time (each now gives up on a table lock after 10 s). They do not update the refresh's skip state; the daily full run (below) covers that, or tick `force`.
- **Skip-unchanged refresh (PR A, 2026-10-06; spec `docs/superpowers/specs/2026-10-06-refresh-io-design.md` rev 2).** The workflow passes `--state-file .ingest-state/state.json`. Before connecting, ingest builds a five-part fingerprint per season: `code` (sha256 of `ingest.py` + `requirements.txt` + pandas/numpy/pyarrow versions), `pbp` / `roster` / `participation` (asset `digest` from the GitHub release API, 3 calls, **exact** asset name, `absent` if not listed), `schedules` (hash of the season's kept `GAMES_COLS` rows — not the `games.csv` digest, which moves with betting lines). Same fingerprint and a full run under 20 h ago → `skipped: sources unchanged`, **no database connection**. Any doubt (API error, missing digest, unreadable state) → normal full run. One run a day is always full (`max skip age`).
- A season's entry is **dropped on disk as soon as an attempt starts** and written back only after its commit, so any failed or interrupted run is followed by a full run. What is recorded for pbp/roster/participation is the **sha256 of the bytes actually downloaded** (`_read_parquet_url` hashes them), and only if it equals the digest the API listed before the run (a re-upload mid-run, a listed participation file that failed to load, a failed schedules ingest → nothing recorded). A state file that cannot be loaded for any reason is removed and means a full run. It lives in the Actions cache (both cache steps are `continue-on-error`): restore with `key: ingest-state-<run_id>-<run_attempt>` + `restore-keys: ingest-state-`, save under the same key after the revalidate step. **The `concurrency: data-refresh` group is what makes a queued run see the previous run's state — never remove it.** Cache evicted (7 unused days) → one full run.
- `changed=` output gates the revalidate POST (`!= 'false'`); a 200 writes `.ingest-state/revalidated_at`, and ingest keeps `changed=true` (even on a skipped run) until a revalidate has succeeded after the last data change. Every run writes one line to the step summary: `2026: skipped…` / `full run (pbp changed): N rows sent` (plus `; next run will also be full (why)` when nothing skippable could be recorded) / `FAILED during a full run (reason for full run: …)` — that bracket is why the run was full, not why it failed. If a run leaves no state file, the workflow saves an empty one (`STATE_TOMBSTONE`) so an older cached state can't be restored instead. To force a run: tick **force** on a manual run (also re-runs the DDL), or delete the `ingest-state-*` caches. Do this after restoring/replacing the database.
- **No DDL on normal runs (PR C).** The `ensure_*` functions run only when `schema_hash` in the state file (sha256 of `ingest.py`) differs, there is no state file, or `--force`: a normal run is 0 DDL statements and 3 commits (was 91 and 21). If a table/column is missing anyway, `run_seasons` catches `UndefinedTable`/`UndefinedColumn`, rolls back and retries the season once with the ensure steps on (`ingest_schedules` heals `games` itself). `data_freshness` has no `ensure_*`, so its absence fails after one retry. **`ensure_games_table` is CREATE-only, so the `games` self-heal cannot add a missing column**: schedules would then fail with a warning on every run (run green, never skipped) until an `ALTER` is added. A policy or index dropped by hand now returns only on the next `ingest.py` change or a forced run. Tests: `tests/test_refresh_io.py`, `test_refresh_ddl.py`, `test_refresh_workflow.py`, `test_refresh_hardening.py` (chaos-test fixes).
- **GitHub auto-disables cron workflows after 60 days without repo activity.** This silently killed the refresh June 1–Sept 5, 2026. The workflow now has a self-keepalive step (re-enables itself via `gh api` each run, needs `actions: write` permission). If the workflow file is ever renamed, update the filename inside the keepalive step.
- **DB blip resilience (PR #30, 2026-10-02):** failures since 9/29 were Supabase-side (open incident "Intermittent latency in Eastern US", worst in EDT working hours): pooler connect errors (`ECHECKOUTTIMEOUT`, `EAUTHQUERY`) and ~60x slowdowns ending in statement timeouts. Healthy runs spend 6–19 s in the DB phase, flat since 9/14 — not our load. `connect_with_retry` (5 tries, waits 30/60/120/240 s, session `SET statement_timeout = 180 s`, needs the session pooler on port 5432), `run_seasons` retries a season from scratch on a fresh connection after 120 s / 300 s on transient DB errors (schedules re-run too), one 24-min run deadline, and `@retry` no longer retries psycopg2 errors (a failed statement aborts the transaction, so in-transaction retries can't work). Usually one retry fits; a severe slowdown can still hit the job's 30-min timeout (rolls back cleanly). To diagnose a failed run: `gh run view <id> --log-failed` and check status.supabase.com incidents. Tests: `tests/test_refresh_resilience.py`.
- `seed.yml` — manual historical backfill. `ci.yml` — lint + tsc + build (placeholder Supabase env vars) + pytest. **CI does NOT run vitest** — run it locally before merging.

## Read resilience PR 1A + 1B (2026-10-06)

- Spec: `docs/superpowers/specs/2026-10-06-read-resilience-design.md` (rev 2; PRs 1A, 1B, 3, 2, 2b). Why: Supabase's REST gateway stalls 1-2 h most days; pages hung, or showed a false 404 / empty tables. **1A = a failed read never looks like an empty one. 1B = every read has a time limit.** Not built yet: PR 3 (sitemap), PR 2 / 2b (caching).
- **1B, the read time limit:** `lib/supabase/timeout.ts` `withReadTimeout(fetch, ms)` wraps the fetch of BOTH clients: 5000 ms in `lib/supabase/server.ts`, 15000 ms in `lib/supabase/client.ts` (it covers the download on the visitor's connection). Any new read gets it with no extra code. A read ends as `TimeoutError: read timed out after 5 s`, an ordinary failed read (1A rules). **A read that passes its own signal (`.abortSignal()`, `fetchAllRows(..., { signal })`) goes through untouched**: that deadline is the only one, so a multi-read assembly with ONE budget (box score, `/team-stats`) must pass its signal to every read (`getAvailableSeasons(signal)` exists for this). The limit is a TOTAL deadline for one read, body included (the wrapper reads the body and returns a new `Response`; each `fetchAllRows` page gets its own 5 s). **It is a race, not only an abort:** Next strips the signal from a fetch that refreshes a stale data-cache entry (`patch-fetch.js`, `signal: isStale ? undefined : signal`), so the timer itself rejects the read; never go back to abort-only. Limits above 60 s are capped.
- **What Next already caches (from source; verify on Vercel before building PR 2):** every page that exports `revalidate = 3600` has its DIRECT Supabase reads in Next's fetch data cache for an hour ("auto cache"), including the `searchParams` pages and `/game` (reading `searchParams` does not turn it off at request time). `/compare` exports no `revalidate`, so its reads are stored for a year until `/api/revalidate` clears them. `/api/health` (`revalidate = 0`) is not cached. So a warm page already survives a stall, and PR 2's request counts ("about 90% fewer reads") must be re-measured from that. The signal's cost (no per-render fetch dedupe) can only show where reads are not cached; it was not observed on pages. **Never put `cache: "no-store"` in the wrapper**: under static generation it throws `DynamicServerError`, which would take `/` and the sitemap out of ISR.
- **Known behaviour, accepted:** `/card` and `/game` wait two limits in a row (about 11 s; `/game` did on main). A dynamic page whose cached reads are stale still gets its data, but Next's own background refresh of those entries runs below the wrapper with no signal (under `next start` the response is held open; on Vercel it goes to `waitUntil`; not verified there). A read that passes its own signal is not raced, so the sitemap's box score probe can still wait for undici's 300 s on a regeneration (PR 3). Timings and the stale-cache run: spec 1.7. Tests: `__tests__/data/supabase-timeout.test.ts` (fake timers work because the wrapper uses `setTimeout`), `__tests__/app/read-timeout-routes.test.tsx`, `__tests__/components/read-timeout-messages.test.tsx`.
- **Loader rule:** every `lib/data` loader throws an `Error` on a query error and returns `[]` / `null` only when the read succeeded with no rows. `getDataFreshness` and `getPlayerBySlug` use `.maybeSingle()`. `fetchAllRows` still rejects with the raw PostgREST object; every loader that calls it rethrows through `queryError(what, err)` (`lib/data/utils.ts`), except `getPlayedRegularSeasonGameIds` (sitemap only, PR 3). `getLatestCardSeason` still returns null on failure, on purpose, and logs it.
- **Input the database would reject must never become a "failed read"** (chaos pass): `/player` and `/team` take `?season=` through `parseSeasonParam` (1999-2100, else the default season); `getPlayerBySlug` returns null without reading for a slug outside `[A-Za-z0-9._'-]{1,100}` (NUL byte, absurd length). **Follow-up (code review M6):** the six season pages and `/compare` still use bare `parseInt` for `?season=` (an out-of-range value there is the error card, as it already was on main); swap to `parseSeasonParam` when next touched. `queryError` / `summarizeUpstreamError` (`lib/data/utils.ts`) show `code`/`details` for a message-less error, turn an upstream HTML page into one sentence, and cut anything else at 300 characters; `/api/health` echoes only that. Never build a loader message from `error.message` directly (a test greps for it).
- **Core vs may-degrade:** a failed core read rejects the page (Next shows that route's `error.tsx`). May degrade, always with `console.error`: team hub slug map and next-season schedule (`getTeamHubData`), the team radar's rows on `/team` (the section shows "The team radar is unavailable right now."; the hub's ten core reads still reject the page), box score link probes, player cross-link boxes and passing map, Game Log official scores, `/compare`'s `p1` lookup. `/team` and `/player` also throw on an EMPTY `data_freshness` list unless `hasNoDatabase()`; `/card`, `/compare` and the season pages keep `fallbackSeason()` for an empty list.
- **Status codes:** a failed read (page or `generateMetadata`) on a route with `loading.tsx` is HTTP 200 + skeleton + error card (empty `<head>` when the metadata read failed); only `/`, `/card`, `/game` return 500. `/api/health` and `/api/stat-card` answer 503 `no-store` (stat-card adds `Retry-After: 60`; 404 only for an unknown slug / no card). OG images built after any failed read carry `cache-control: no-store` (unit-tested; not checked on Vercel yet). **next/og header trap:** `ImageResponse` spreads the caller's headers over its own LOWERCASE `cache-control` one-year default, so only a lowercase key replaces it; a `"Cache-Control"` key sends both, joined (still true of the stat-card download's success path, pinned as known debt in `stat-card-route.test.ts`). Test mocks of `next/og` must merge headers the same way.

## Game Log scores (box scores Phase 0)

- **The Game Log's Result cell reads the official final score from `games`**, not the weekly rows' stored `team_score`/`opponent_score`. Those stored columns come from `_derive_game_context` over *filtered* plays, which misses points scored after the last run or pass: **31 of 2025's 272 games are stored with the wrong score (28 with the wrong W/L/T)** — e.g. Josh Allen's 2025 week 1 is stored L 38-40, really W 41-40. The columns were NOT rewritten (no production write); anything else that reads them gets the wrong score. The backfill is the natural time to fix the stored values.
- Flow: `app/player/[slug]/page.tsx` collects every distinct `team_id` in the weekly rows → `getGameResults(teamIds, season)` (`lib/data/games.ts`) → `{ [team_id]: { [week]: GameResult } }` → `PlayerPageContent` → `GameLogTab`. **Rows look themselves up by their own `team_id` + `week`, never `player.current_team_id`** (a traded player's rows span teams), and trust the entry only when the opponent matches.
- Fallback: no matching schedule game, or the `games` read failed → the row's stored score, exactly as before. ## team_game_stats + QB rushing EPA (box scores PR 2)

- **`team_game_stats`** (18th Supabase table): one row per team per played REG game, key `(game_id, team_id)` + `season, week, opponent_id, home_away`; the 64 columns (62 + `designed_runs`/`stuffed_runs`, see "Team Radar" below) are `TEAM_GAME_STATS_COLS` in `scripts/ingest.py`. Built by `aggregate_team_game_stats(pbp, season)` from the **RAW** pbp frame (never `filter_plays` output — possession, drives, penalties and red zone need kicking and `no_play` rows). Efficiency set = `pass == 1 | rush == 1` with EPA present (2-pt KEPT, kneels drop out, penalty-wiped passes stay in with 0 yards); traditional set = official ESPN conventions (spec §4). Every column is pinned against rbsdm/ESPN for `2026_01_BUF_HOU` in `tests/test_team_game_stats.py` — never edit a `GOLD` value to make a test pass.
- **Three play counts disagree on purpose**: efficiency plays (BUF 56) ≠ total plays (52 = rush att + pass att + sacks) ≠ rush plays (19) beside rushing attempts (21 = 19 + 1 kneel + 1 scramble). `first_downs` is the SUM of pass/rush/penalty parts (one play can be both), `sack_yards` is stored POSITIVE, `time_of_possession_seconds` sums `drive_time_of_possession` once per `drive` (never `fixed_drive`), `team_targets` is exactly the receiver aggregator's target set (the TGT% denominator).
- **NULL policy**: counts/yards 0, `epa_lost_*` 0.0, the 17 rate columns (`TEAM_GAME_STATS_RATE_COLS`) None when the denominator is 0, `time_of_possession_seconds` None only for a team with drives but *no* readable clock — and when only SOME of a team's drives have one, the sum is short, so `aggregate_team_game_stats` logs a `WARNING` naming the game and team rather than understating possession silently. Those columns are built as `dtype=object` Series so None survives (a list of floats + None becomes float64/NaN → `'NaN'::numeric`); `upsert_team_game_stats` converts NaN→None and numpy→Python itself (same reasoning as `ingest_schedules`).
- **Known limitations**: turnovers are keyed by `posteam`, so a punt the RECEIVING team muffs (`2026_01_CHI_CAR`) is credited to nobody — a strict xfail in `tests/test_team_game_stats.py`.
